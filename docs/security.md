# Security model

Background is in ADRs 0004, 0006, 0015, 0016, 0028, 0029, 0030 and 0033.

## Assets
- The **press capability**: whoever can press, gets a fresh code.
- The **codes and photos** shown on the display.
- **Pairing keys**, the controllers' and the device's **signing keys**, and **broker credentials**.

## Trust boundaries
| Party | Trusted? | Can see | Can do |
|---|---|---|---|
| Paired controller (holds `K`, and the bound signing key in its phone's Keystore) | yes | everything for its pairing | press, take a calibration photo, change the calibration, ask for status |
| Someone with `K` but not the signing keys: a photographed QR, a copied blob, a memory dump (ADR 0033) | no | recorded commands | nothing on the device: commands not signed by the bound key are dropped. While the QR is still shown and before the controller binds: bind first, which the fingerprint comparison exposes. Nothing on the controller either: every event needs the device's signature over its job's key exchange, so even with the device's broker credential or the relay's help they can't answer in the device's place (a false code, photo, status or `bound`), only drop or delay events, as the relay can |
| Relay (EMQX Cloud) and network | **no** | topic IDs, message sizes, timing, IP addresses, the online flag, broker usernames | drop or delay messages (denial of service) |
| Someone with the broker credentials but no `K` (a lost or revoked controller phone, until the credential is rotated) | no | the same as the relay, limited by the broker's authorisation rules | publish garbage, which is dropped; flood the broker |
| Someone within Bluetooth range of the Bot | no | nothing | press the button with any BLE app if no Bot password is set; with one, replay a press they recorded (ADRs 0003, 0025) |
| Physical access to the device phone and its screen-lock PIN | yes, by design, unless an app PIN is set (ADR 0015) | everything | pair new controllers |
| Physical access to the device phone without its screen-lock PIN | no | the lock screen; the service keeps running if it was | nothing; after a reboot the device stays offline until someone unlocks it (ADR 0028) |
| Someone holding an unlocked controller phone | no, if an app PIN is set | the screen-lock prompt, then the app PIN prompt | guess the app PIN: 3 tries, then a wipe or growing waits |
| Someone with `adb` access to a phone | no, on a release build | the preferences and the encrypted blob, which stays encrypted | nothing further; on a debug build, `run-as` reads the diagnostics and decrypts the blob (ADRs 0024, 0026) |
| Someone with root on a stolen locked phone, without its screen-lock credential | no | the wrapped data key and the encrypted blob; the Keystore key won't unwrap without a fresh screen-lock authentication (ADR 0028). On the device phone, and on a controller with the app open or its data key not yet forgotten, the data key in the app's memory | with the data key: decrypt recorded commands (not status replies, codes or photos, ADRs 0030, 0033), flood the broker until the credential is rotated. Pressing needs the signing key too, which stays in the controller's secure hardware: root on a locked controller phone can't sign on Android 9 and later, and before that only on that phone and within 5 min of its last unlock (ADR 0033). Root on the running device phone can do whatever the device app does, signing as the device included: the device's key needs no unlock |

## Properties
- **Confidentiality and integrity:** XChaCha20-Poly1305 with keys derived per direction and per pair. The additional authenticated data binds each message to its version, device, controller and direction.
- **Replay protection:** a strictly increasing `seq` per controller (persisted), plus a ±120 s timestamp window. Events carry neither: job IDs are random, travel encrypted and are known to the controller only while the job runs, so a replayed event matches nothing.
  - A captured command can't be replayed, even within the window.
  - Testing: `RelayIntegrationTest` re-publishes captured commands and checks they are ignored.
- **Authorisation:** pairing needs the QR code shown on the device screen, and the controller's `bind` while it is shown, within 10 min. The first bind wins; from then on the device takes only commands signed by that controller's key, so the QR is worthless (ADR 0033). Both phones show the key's fingerprint. Revoking deletes the controller's pairing on the device, after which its commands are ignored.
- **Command signatures (ADR 0033):** every command is signed with ECDSA P-256 by a key that can't leave the controller phone's secure hardware, then encrypted, so the relay never sees the signature and only a holder of `K` gets as far as the signature check. Pairings made before ADR 0033 take no commands and must be paired again.
- **Event signatures (ADR 0033):** the device signs each job's key exchange (both ephemeral keys, both IDs and the job ID) once, with an ECDSA P-256 key that can't leave the device phone's secure hardware, and every event of the job carries that signature inside the encryption. The controller checks it against `devicePub` from the pairing QR on the first event of the job that opens, and drops events that don't carry it. So only the device can answer: someone holding `K` can't forge a code, photo, status or `bound`, even with the relay's help. Version 1 and 2 events, which carried no signature, are refused.
  - **Forgery warning:** an event that opens under a job's key but lacks the device's signature takes `K`, and so does a `bind` the device answers with another key's fingerprint. The controller counts both and, while it has counted any for the selected pairing, shows *Answers not signed by the device were dropped…* and asks for the controller to be revoked on the device and paired again. The count is in memory, per pairing, until the app's process ends or the pairing is removed; nothing is written to disk. What the relay alone can send isn't counted: bytes that open under no open job (junk, replays, late answers), older envelopes, and the online flag. A device that replaced its signing key while controllers were bound (the Keystore called it permanently invalidated) brings the same warning on every answer, and the same remedy applies. The log lines (`adb logcat -s RPB`) name the reason only, never keys, codes, IDs or payloads.
- **Fresh status (ADR 0033):** a status request is a job of its own, and the controller takes a `status` only as the answer to a request it has open, for 15 s, and never an older request's answer over a newer one's. The device never sends one unasked, so an old status held back by the relay can't be passed off as current.
- **At rest (ADRs 0028, 0029):** keys and broker credentials are encrypted with a random AES-256-GCM data key, which an Android Keystore key wraps. That key needs the phone's screen lock passed within the last 30 s, so both phones need a screen lock; it lives in StrongBox where the phone has one, the TEE otherwise, shown as *Key storage* in the PIN lock settings. The app unwraps the data key once per process and keeps it in memory. A controller forgets it when it leaves the screen with no app PIN, or after 60 s away with one, and asks for the screen lock again on return if the 30 s have passed. The device phone keeps it while the service runs; after a reboot or a crash it waits for an unlock. Removing the screen lock invalidates the key, which loses the pairings. On a controller, each pairing also has a signing key (ADR 0033): EC P-256, sign only, not exportable, in StrongBox where the phone has one and the TEE otherwise. It signs only within 5 min of the screen lock or a strong biometric, so after 5 min a press asks for the screen lock first; a newly enrolled fingerprint doesn't invalidate it, removing the screen lock does. On Android 9 and later it also signs only while the phone is unlocked. Removing a pairing or a wipe deletes it, and keys with no pairing, left by a pairing cut short, are deleted when the controller's secrets open. The device phone has one signing key of its own (ADR 0033): EC P-256, sign only, not exportable, in StrongBox where the phone has one and the TEE otherwise, and with no user authentication, as the device runs unattended. A wipe deletes it; the new key after a wipe means pairing every controller again. The controller keeps no codes or photos on disk: its history is in memory only, each entry for 5 min, and cleared when the PIN lock engages (ADR 0026). Nothing is included in cloud backup or device-to-device transfer, so a new phone starts unpaired (ADR 0020).
- **Forward secrecy for events (ADR 0030):** the events of each job go under a key from ephemeral X25519 keys of both sides; the private keys are erased once the job key is derived, and the job key is dropped when the job ends, so recorded codes, photos and status replies stay sealed if `K` leaks later. Commands stay under `K`.
- **App PIN lock (optional, ADR 0015):** asked on start and after more than 60 s away, after the screen lock where that is needed. The PIN is stored as a salted PBKDF2 hash in the encrypted blob, and failures are counted before checking. With wipe on, 3 wrong PINs erase all app data and the Keystore key; with wipe off, waits grow from 30 s to 1 h, measured on the time since boot, so setting the clock forward doesn't skip them (ADR 0024).
- **Broker access (ADR 0024):** the device's MQTT client ID is random and secret, so nobody can take its session over; authorisation rules on the broker keep each credential to its own topics; the device never logs a code to logcat.
- **Builds:** the phones run signed release builds, so `adb shell run-as` can't reach the app's files or act as its UID (ADR 0024).
- **Screen capture (ADR 0020):** `FLAG_SECURE` blanks the Recents thumbnail and blocks screenshots and screen recording in both modes, so the last code or a pairing QR doesn't linger on screen.
- **Clipboard:** a copied code is marked sensitive, so Android 13 and later hide it in the clipboard preview.
- **No inbound ports** on either phone.

## Known limitations
- **Forward secrecy covers events only:** someone who records traffic and later steals `K` can read the commands (when presses happened, the delays, calibrations), but not press, which needs the controller's signing key, nor answer, which needs the device's (ADR 0033).
- **The device's signing key is as safe as the device phone (ADR 0033):** root on it, or an exploit of its secure hardware, signs as the device; whoever has that can already press the button. The key needs no unlock, so a device phone that restarts keeps answering.
- **Keys in memory:** root on the running device phone, or on a controller while the app is open, reads the data key from memory. When a controller locks, the data key is zeroed, but the decrypted secrets (strings) and `K` inside the crypto library can only be dropped: they stay in the heap until the garbage collector reuses it, and so does a finished job's key. The signing keys never enter memory. A phone whose Keystore is in software (shown as *Key storage: software*) gives root the wrapping key and the signing keys too.
- **The device needs a person after a reboot or a crash** (ADR 0028): until someone unlocks it, it stays offline.
- **Metadata:** the relay learns when presses happen and roughly how big the photos are.
- **Shared controller credential:** all controllers use one broker credential. It only gates broker access, not commands. Revoking a controller doesn't revoke it: after a lost phone, rotate it on the broker and pair the other controllers again.
- **Pairing QR leaks, during the bind window only (ADR 0033):** someone who scans the QR before the legitimate controller, while the dialog is open, binds first; the legitimate controller's bind then fails while the device shows *Bound* with the other phone's fingerprint. If the device answers the legitimate controller's bind with the other key's fingerprint, the controller says so and asks for that controller to be revoked on the device. Compare the fingerprints on both phones, and close the QR dialog once bound. The dialog keeps the screen on; turning the screen off or leaving the app before the bind cancels the pairing. After the bind, a copy of the QR gives `K` (recorded commands) but no presses and no forged events.
- **Root on a stolen controller phone (ADR 0033)** can sign commands only on that phone, only within 5 min of its last unlock, and on Android 9 and later only while it is still unlocked; after that the secure hardware refuses without the screen-lock credential. Revoke the controller on the device.
- **No key attestation:** the device doesn't check that a controller's key is in secure hardware, nor the controller that the device's is; each trusts the app that made the key.
- **Calibration from any controller (ADR 0016):** any paired controller can change the calibration. A bad one makes reads fail or, at worst, read wrongly; the photo is always sent, and the device refuses calibrations that would break the reader. The calibration itself carries no code.
- **Diagnostics (ADR 0023):** with **Save diagnostics** on, the device keeps its newest full-size photos, which show codes, in app-private storage for `adb`. Off by default; turning it off deletes them. They are never sent.
- **Display anchor (ADR 0018):** to follow the display, the device keeps a reduced picture of the area around the digit row, with the digits blanked. It is stored in the encrypted settings and never sent.
- **Display limits:** a physically missing segment on the display can produce a confidently wrong digit (ADR 0008). The photo is always sent so the user can check.
- **App PIN strength:** the PIN hash alone wouldn't resist offline guessing. It relies on the Keystore encryption of the blob, now behind the screen lock, and the attempt limit.
- **Old phone:** the device phone gets no OS updates. Keep it dedicated to this app, with no accounts or other apps, and USB debugging off once set up.
- **Bot in Bluetooth range:** without a password, the SwitchBot Bot takes presses from anyone in range. Its password (ADR 0025) goes over the air as a CRC32, the same every time, so a recorded press can be replayed. Set it, and mount the Bot where strangers don't get within a few metres.
