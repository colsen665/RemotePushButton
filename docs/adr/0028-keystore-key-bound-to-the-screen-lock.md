# 28. The Keystore key needs the screen lock; both phones keep one; the device needs an unlock after a reboot

- Status: Accepted; amended by [0033](0033-controllers-bound-to-a-hardware-key.md) (a signing key per pairing on the controller, a signing key on the device)
- Date: 2026-11-03
- Amends: [0002](0002-old-android-phone-as-device.md) and [0009](0009-device-app-as-home-launcher.md) (the device no longer recovers from a reboot on its own), [0006](0006-e2e-crypto-and-qr-pairing.md) (keys at rest), [0015](0015-app-pin-lock-with-optional-wipe.md) (what the app PIN protects against), [0024](0024-relay-hardening-and-release-builds.md) (the device phone's screen lock)

## Context
The secrets blob (pairing keys, broker credentials, the PIN hash, the anchor) is encrypted with an Android Keystore AES-GCM key that has **no user-authentication requirement**. The key can't be exported, but it can be used by any code running as the app's UID, and on a release build that means root. A stolen phone that has been unlocked once since boot keeps the blob readable (file-based encryption, credential-encrypted storage), so whoever gets root on it, which is what forensic tools do, can ask the Keystore to decrypt the blob and walks away with every pairing key and the broker credential. With a controller's key they can press and get fresh codes until the controller is revoked on the device phone; with the device phone's blob they hold every controller's key and the device credential.

The app PIN (ADR 0015) doesn't help here: it is a UI gate, and the blob is decrypted when the process starts, PIN or not.

The device phone has run **without a screen lock** (ADR 0024, `docs/setup.md` §4) so that it comes back online by itself after a reboot, as the HOME launcher (ADR 0009). That is what stops the Keystore key from being tied to a screen lock on that phone.

## Decision
- **The Keystore key requires a recent screen-lock authentication.** `setUserAuthenticationRequired(true)` with a validity window of 30 s: on API 26–29 `setUserAuthenticationValidityDurationSeconds`, on API 30 and later `setUserAuthenticationParameters(30, AUTH_DEVICE_CREDENTIAL or AUTH_BIOMETRIC_STRONG)`, with `setInvalidatedByBiometricEnrollment(false)` so adding a fingerprint doesn't lose the pairings. The secure hardware then refuses to use the key unless the screen lock was passed within the window.
- **A data key in between.** A random 256-bit data key encrypts the blob (AES-256-GCM, the same on-disk format as today); the Keystore key only wraps the data key. The app unwraps the data key **once per process**, at start, and keeps it in memory. Every later save (anchor, calibration, PIN counters, settings) uses the data key and never touches the Keystore, so the window has to cover the start only, and the device service keeps saving while the phone is locked.
- **The controller forgets the data key when it locks.** When the PIN prompt appears (on start, or after more than 60 s away, ADR 0015), or when the app goes to the background with no PIN set, the controller zeroes the data key in memory and drops the decrypted secrets, along with the history (ADR 0026). On return it unwraps the key again through the Keystore: silently within the window, otherwise after the prompt below. The device phone can't do this: its service needs the key while nobody is there.
- **When the key refuses** (`UserNotAuthenticatedException`), the app asks for the screen lock itself: `BiometricPrompt` allowing the device credential on API 30 and later, `KeyguardManager.createConfirmDeviceCredentialIntent` before, then tries again. So a controller user who unlocked the phone minutes ago gets one prompt when the app opens, not a failure.
- **Both phones have a screen lock.** Setup sets one before the mode is chosen. Without one Android can't create the key; the app says so instead of failing. Removing the screen lock later permanently invalidates the key, which is the same as a wipe: the app explains that the data is gone and starts at mode selection.
- **The device phone needs a person after a reboot or a crash.** After a reboot, the phone stops at its lock screen; once unlocked, the HOME launcher opens the app, which reads its settings and starts the service as before. If Android restarts the service alone while the phone is locked (after a crash), the service can't read its settings: it posts a notification *Unlock the phone to bring the device back online*, waits for `ACTION_USER_PRESENT` or the screen coming on, and then starts properly. Until then the device shows as offline on the controllers. The 12 h idle test (`TODO.md`) found no restart, so this is expected to be rare.
- **The app PIN stays as it is**, optional in both modes. It covers a phone handed over unlocked and the 60 s away rule; the screen lock now covers the keys at rest. A controller user who finds two PINs too many leaves the app PIN off.
- **Migration.** On the first start after the update, with the user present: decrypt the blob with the old key, create the new key (StrongBox-backed where possible, ADR 0029), wrap a fresh data key, write the blob again, delete the old key. The new key needs a screen lock first, so the setup for the update says to set one.
- **Secure hardware is checked.** `KeyInfo.isUserAuthenticationRequirementEnforcedBySecureHardware` is logged and shown in the PIN lock dialog as *Key storage: StrongBox / hardware / software*, or *unknown* when the Keystore doesn't say. On a phone where it is software, root still gets everything, as before.

## Consequences
- **A stolen locked phone gives up nothing without its screen-lock credential**, even to root: the secure hardware checks the authentication, not the app. The screen lock itself is rate-limited by the OS. What remains is an exploit of the secure hardware, which ADR 0029 narrows.
- **A controller phone stolen unlocked** gives up its keys only while the app is open with the data key in memory. Once the app has locked, or gone to the background without a PIN, root finds a wrapped key that the secure hardware won't unwrap without the screen-lock credential. The device phone keeps its data key in memory for as long as the service runs, which this decision accepts.
- **The device no longer recovers on its own.** After a power cut, a reboot or a crash while nobody is there, it stays offline until someone enters the phone's PIN. This is accepted: the device phone sits at a site where someone can reach it, and the alternative was leaving every controller's key one root exploit away.
- **Two PINs on the device phone:** the phone's, now required, and the optional app PIN. The app PIN is still what protects the pairing QR and the settings from someone handed the unlocked phone (ADR 0015).
- **USB debugging authorisation on the device phone now sits behind the screen lock** too, which ADR 0024 couldn't rely on. USB debugging stays off all the same.
- **Removing the screen lock loses all pairings** on that phone. The setup says so.
- **One more secret to keep:** the device phone's screen-lock PIN. Someone holding the device phone and that PIN is trusted, as physical access was before (ADR 0015).
- **Old controller phones (API 26–29)** get the keyguard intent instead of `BiometricPrompt`; both work with a PIN, pattern or password.

## Alternatives
- **Wrap the blob with the app PIN as well** (PBKDF2 of the PIN mixed into the data key). It only matters to a thief who already has root plus the screen-lock credential or an exploit of the secure hardware, and then 4–8 digits fall to offline guessing in seconds to an hour on a GPU. It would also move the attempt counter out of the blob, make the app PIN mandatory, and have the device phone ask for two PINs after every reboot. Forgetting the data key on lock covers the realistic case, a phone taken unlocked, at no cost.
- **Per-use authentication** (a `BiometricPrompt` with a `CryptoObject` for every key use): the data key makes it one use per process anyway, and the timeout key with a fallback prompt also works on API 26–29.
- **`setUnlockedDeviceRequired(true)`** (API 28): redundant with the window, since the key is used only right after an unlock, and it would complicate the migration.
- **Bind only the controller's key and leave the device phone without a screen lock:** the device blob is the bigger prize, it holds every controller's key and the device credential, so that would protect the smaller half.
- **Replace the controller's app PIN by the OS prompt:** possible later, as a usability change; not needed for the security goal.

## Implementation notes
- **A controller with an app PIN forgets the data key 60 s after leaving the screen**, when the PIN would be asked again, not only when the PIN prompt next appears. Otherwise a phone taken unlocked with the app in the background would keep the key in memory until someone opened the app.
- **The order on return** is the screen lock first, then the app PIN: the PIN hash is in the blob the data key opens.
- **Zeroed, or only dropped.** Closing zeroes the data key's bytes. The decrypted secrets are strings (the pairing codes hold `K`), and the controller's client keeps `K` inside Tink objects; neither can be zeroed, so they are dropped and stay in the heap until the garbage collector reuses it. Root on a controller shortly after it locked may still find them.
- **Whatever a retry won't fix opens as lost:** an invalidated key, but also a damaged blob or wrapped key and an unexpected Keystore error. The app shows the erase screen, with *Try again* for a Keystore error that passes, instead of crashing. The log names only the exception classes, since a parser's message can quote the decrypted blob.
- **The device service stops waiting** when the key is lost or there is no screen lock, which no unlock fixes: it leaves an *Open the app* notification and stops, releasing its wake and Wi-Fi locks. The app's device screen starts it again once the secrets open.
- **A first start makes the key afresh** each time it hasn't saved a wrapped data key yet, replacing any key a failed attempt left behind, which may have died since.
- **Opening saves the blob back only when decoding filled in a default** (the re-encoded blob differs from the stored one), so a controller returning to the app costs one unwrap and one decrypt, not a write.
- **The vault is in `core`** (`SecretVault`, behind `KeyWrapper` and `VaultFiles`, with tests); the app supplies the Keystore key and the preferences. While it is closed, saves change nothing and report it, since a UI callback can still arrive after the controller locked.
